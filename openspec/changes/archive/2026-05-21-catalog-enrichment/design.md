## Context

The AI Data Mapper's catalog page (`ui/pages/catalog.py`) currently provides a minimal YAML-backed editor for table/column descriptions. Catalogs are auto-generated by `catalog_builder.py` which extracts schemas and optionally enriches with column statistics. The catalog YAML files already contain rich metadata (row counts, null counts, distinct counts, sample values, PK/FK relationships) but the UI displays none of it.

Two types of database connectors exist: DuckDB and Snowflake (live databases) and ExcelSchemaConnector (metadata-only). The Excel connector already extracts `description` fields from the spreadsheet. The DuckDB and Snowflake connectors do not extract `COMMENT` metadata despite both databases supporting it.

User-edited descriptions are currently written directly into the catalog YAML. This means a catalog rebuild (triggered by schema hash change) overwrites all manual work.

The LLM infrastructure (Azure OpenAI) is already configured in `project.yaml` under the `agent` block and used by mapping agents, chat agent, CRR agent, and DPM agent.

## Goals / Non-Goals

**Goals:**
- Extract source database comments from DuckDB and Snowflake into catalog `description` fields
- Separate user-authored metadata into overlay files that survive catalog rebuilds
- Surface catalog stats, relationships, and source descriptions on the catalog page
- Enable AI-assisted description generation using the existing LLM infrastructure
- Show description coverage metrics

**Non-Goals:**
- Configurable/dynamic annotation field types (future TODO — start with hardcoded `user_description` + `mapping_instructions`)
- Glossary integration for AI descriptions
- Production-grade concurrency or locking on annotation files
- Full-text search or filtering across the catalog (separate change)

## Decisions

### 1. Annotation overlay files

**Decision**: Store user/AI-authored metadata in `<name>.annotations.yaml` files alongside catalog YAMLs, not inline.

**Rationale**: `catalog_builder.py` regenerates catalog YAMLs from scratch when the schema hash changes. Inline annotations would be lost. A separate file keyed by `schema.table` and column name is independent of the catalog structure.

**Structure**:
```yaml
version: 1
dataset: banking
annotations:
  src.accounts:                          # key: schema_name.table_name
    user_description: "Core account master..."
    mapping_instructions: "Map to BIRD IL..."
    columns:
      account_id:
        user_description: "Unique hex identifier..."
        mapping_instructions: "VARCHAR 16-char hex. No transform."
      counterparty_id:
        user_description: "Links to counterparty entity..."
        mapping_instructions: "FK to counterparties. Never NULL."
```

**Alternatives considered**:
- Inline in catalog YAML: simpler code, but destroyed on rebuild
- Separate DB (SQLite): overkill for a PoC with YAML-based architecture

### 2. Comment extraction approach

**Decision**: Add a new `fetch_comments()` method to `BaseConnector` returning `{table_name: {comment, columns: {col_name: comment}}}`. Call it from `extract_schema_from_db()` and merge comments into the schema structure as `description` fields.

**Rationale**: `_fetch_schema_rows()` returns a fixed 6-tuple. Adding a 7th element would break the shared `_build_schema_structure()` helper. A separate method is cleaner and opt-in (connectors that don't support comments return empty dicts).

**Implementation**:
- DuckDB: query `duckdb_tables()` and `duckdb_columns()` for `comment` field
- Snowflake: query `information_schema.tables.COMMENT` and `information_schema.columns.COMMENT`
- ExcelSchemaConnector: already handles descriptions via `get_schemas()` override — no change needed

### 3. AI generation scope

**Decision**: Generate descriptions per-table (one LLM call produces descriptions for all columns in a table). Allow triggering at per-column level (sends same table context, asks for one column) and per-table level (batch all columns).

**Rationale**: The LLM needs table context (sibling columns, relationships) to produce coherent descriptions. Per-column calls would repeat this context. Per-dataset would exceed token limits for large schemas.

**Prompt context includes**:
- Table name, schema name, all column names + types
- Column stats (distinct count, null %, min/max, sample values)
- PK/FK relationships
- Source descriptions (if available)
- User-provided optional instructions

### 4. AI agent location

**Decision**: Create `agents/catalog_agent.py` with a `generate_descriptions()` function. Reuse the `agent` config from `project.yaml` for LLM settings.

**Rationale**: Follows the existing pattern (mapping_agent, chat_agent, etc.). The catalog agent is simple — no tool calling, no multi-turn — just a single prompt→response.

### 6. Source description display

**Decision**: Show source descriptions as read-only text (not editable). Same treatment for all datasets — if no source description exists, the field is simply empty/hidden.

**Rationale**: Source descriptions are authoritative metadata from the source system. Users should see them as context but edit only the annotation fields. No special-casing per dataset.

## Risks / Trade-offs

- **[Annotation file drift]** → If columns are renamed or tables dropped, annotation keys become orphaned. Mitigation: acceptable for PoC; a future cleanup utility could prune orphaned keys.
- **[LLM cost on batch generation]** → "Generate all" on a large table (100+ columns) could be expensive. Mitigation: use `gpt-5.4-mini` (cheap), warn user before batch generation, respect `min_request_interval`.
- **[DuckDB comment support]** → DuckDB's `COMMENT` feature may not be present in older versions. Mitigation: wrap in try/except, fall back to no comments. The demo DB likely doesn't have comments set anyway — this is primarily for Snowflake and future real-world use.
- **[Streamlit layout complexity]** → The richer layout with multiple zones, toggles, and inline stats may hit Streamlit's layout limitations. Mitigation: progressive enhancement — start with the essentials, add polish iteratively.
